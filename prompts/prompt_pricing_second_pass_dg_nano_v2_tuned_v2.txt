=== EVIDENCE / ANCHOR RULES (HIGHEST PRIORITY) ===

- "flat": fixed rates, no tiers.

=== METRICS ===
Only define a metric if it is directly used in a tier condition or a rate condition.

metrics[] item shape:
{

Rules:

- Metric naming MUST represent a tier/rate **driver variable**, not an outcome label.
  - BAD metric names: "PricingLevel", "PricingRegime", "PricingTier", "ApplicableMarginLevel".
  - BAD metric names also include literal contract labels such as "APPLICABLE PRICING LEVEL", "PRICING LEVEL", "LEVEL I STATUS" when used as standalone metric names.
  - GOOD metric names: leverage ratio term, coverage ratio term, rating/status code term, amendment effective date term.
  - Exception: ratings-based schemes may use rating/status driver labels when that is the explicit contract driver.
- Ratings-based normalization:
  - If tiers are status buckets (e.g., "Level I Status" ...), DO NOT emit one metric per level label.

=== HOW TO INTERPRET TABLES (MOST IMPORTANT) ===
Tables come in two common shapes:

(A) ROWS ARE TIERS (metric bucket rows)
Example headers: "Debt/Cash Flow Ratio | Applicable Margin", or
  "Consolidated Secured Net Leverage Ratio | Base Rate Loans | Eurocurrency Rate Loans"
In this case:
- Each row after the header is ONE tier.
- The tier’s conditions come from the row bucket text (e.g., ">= 3.00:1.0", "< 3.00:1.0").
- Each non-first column corresponds to a separate rate series:
  - "Base Rate Loans" => a margin rate with base_rate="Base Rate" (base_rate_type="prime")
  - "Eurocurrency Rate Loans" => a margin rate with base_rate="Eurocurrency Rate" (base_rate_type="libor" if "LIBOR"/"Eurocurrency" appears)
  - "Commitment Fee" => a fee rate with fee_basis="undrawn" or "facility_commitment" (choose the best match from text)

(B) COLUMNS ARE TIERS (status columns / rating columns)
Example: columns "Level I Status ... Level VI Status" and rows like:
  "Term Benchmark Loans, RFR Loans, and Money Market Loans" and "ABR Loans ..."
In this case:
- Each column heading is ONE tier (tier_id can be "Level I Status" etc).
- Row labels correspond to separate rates:
  - Row contains "Term Benchmark" or "RFR" => margin rate, base_rate="Term SOFR" if present, else "Term Benchmark"
  - Row contains "ABR" => margin rate, base_rate="ABR" (base_rate_type="prime")
  - A separate single-row table referenced as "Facility Fee Rate" => fee rate, fee_basis="facility_commitment"
  - "L/C Fee Rate" tables => fee rate, fee_basis="letters_of_credit"

=== MULTI-REGIME PRICING (AMENDMENT PERIODS) ===
If the input shows multiple distinct pricing regimes (e.g., “prior to X”, “on or after Y”, “before the Revolving Facility Amendment Date”, etc.):
1) Create one tier_scheme PER regime (scheme_id may end with "_P1", "_P2", ...).
2) Do NOT create synthetic outcome metrics like "PricingRegime" or "PricingLevel".
3) Only use `condition` on rate objects when you can name a concrete driver metric from the agreement text
   (for example a rating/status metric, leverage metric, or explicit amendment-effective-date term).
4) If regime split exists but no single driver metric is explicitly named, omit `condition` and encode separation via
   distinct `tier_scheme_ref` + `rate_id`, with regime evidence in `source_refs`.
