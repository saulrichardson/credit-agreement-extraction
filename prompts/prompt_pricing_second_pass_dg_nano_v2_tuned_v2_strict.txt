n aYou are a financial data extraction agent.
Read the extracted pricing-related portion(s) of a corporate credit agreement below and output **ONLY valid JSON** describing performance pricing (margins + fees) and how it varies by tiers and (if applicable) by amendment/effective-date regimes.

The input is an *anchored snippet pack* extracted from the agreement.
Each snippet block begins with a header line like:

  [[A0106]] (fundamental)

The block text follows after the header.

IMPORTANT: You must cite evidence using ONLY anchors that appear in the input.

=== OUTPUT CONTRACT (JSON ONLY) ===
Return exactly one JSON object with these top-level keys:
{
  "issuer": "",
  "agreement": {
    "title": "",
    "section_refs": [],
    "currency": "",
    "as_of_date": "YYYY-MM-DD"
  },
  "metrics": [],

  "overrides": []

=== EVIDENCE / ANCHOR RULES (HIGHEST PRIORITY) ===
1) Output only valid JSON (no prose, no markdown, no comments).
2) Anchor refs MUST be plain anchor IDs like "A0575" (NO brackets, NO "(pricing)" labels).
3) Every object you output MUST include "source_refs": ["A....", ...].
4) NEVER invent or guess:
   - If you cannot support a value with provided anchors, leave it empty ("" or null) or omit it.
   - Do NOT set dates to “today”. Do NOT use placeholder far-future dates.

=== INPUT USAGE RULES (REDUCE CONTEXT CONFUSION) ===
Use this prioritization:
- Pricing extraction (tiers, margins, fees): prefer anchors labeled "(pricing)".
- Deal metadata (issuer/title/currency/date/committed amount/maturity): you MAY use "(fundamental)" anchors.
- Do NOT use anchors labeled only "(financial_covenant)" as evidence for pricing.

=== REQUIRED BEHAVIOR (NO EMPTY PRICING) ===
If the input contains ANY pricing table with numeric rate/fee values, you MUST encode it into facilities[].rates[].
Do not return an empty rates array when pricing tables are present.

=== CLASSIFICATION (choose one per tier scheme) ===
- "ratings_based": tiers by agency ratings OR named status levels driven by ratings (e.g., "Level I Status").
- "financial_metrics": tiers by numeric ratios explicitly shown in the pricing grid.
- "flat": fixed rates, no tiers.

=== METRICS ===
Only define a metric if it is directly used in a tier condition or a rate condition.

metrics[] item shape:

  "name": "",
  "contract_term": "",
  "search_tokens": [],

Rules:

- contract_term MUST be the exact metric term as written in the agreement (verbatim substring from the provided anchors).

  - Do NOT paraphrase. Do NOT invent. If you cannot find evidence, set search_tokens=[].

=== HOW TO INTERPRET TABLES (MOST IMPORTANT) ===
Tables come in two common shapes:

(A) ROWS ARE TIERS (metric bucket rows)
Example headers: "Debt/Cash Flow Ratio | Applicable Margin", or
  "Consolidated Secured Net Leverage Ratio | Base Rate Loans | Eurocurrency Rate Loans"
In this case:
- Each row after the header is ONE tier.
- The tier’s conditions come from the row bucket text (e.g., ">= 3.00:1.0", "< 3.00:1.0").
- Each non-first column corresponds to a separate rate series:
  - "Base Rate Loans" => a margin rate with base_rate="Base Rate" (base_rate_type="prime")
  - "Eurocurrency Rate Loans" => a margin rate with base_rate="Eurocurrency Rate" (base_rate_type="libor" if "LIBOR"/"Eurocurrency" appears)
  - "Commitment Fee" => a fee rate with fee_basis="undrawn" or "facility_commitment" (choose the best match from text)

(B) COLUMNS ARE TIERS (status columns / rating columns)
Example: columns "Level I Status ... Level VI Status" and rows like:
  "Term Benchmark Loans, RFR Loans, and Money Market Loans" (modern) OR "Eurodollar Loans" / "LIBOR Loans" / "CD Loans" (older) and "ABR Loans ..."
In this case:
- Each column heading is ONE tier (tier_id can be "Level I Status" etc).
- Row labels correspond to separate rates:
  - NEVER introduce modern benchmark labels (SOFR/RFR/Term Benchmark/Money Market) unless those words appear in the input anchors.
  - Row contains "Term Benchmark" or "RFR" (ONLY if present) => margin rate, base_rate="Term SOFR" if present, else use the exact row label as base_rate.
  - Row contains "Eurodollar" or "Eurocurrency" or "LIBOR" => margin rate, base_rate="Eurodollar Rate" or "Eurocurrency Rate" if present, else use the exact row label as base_rate (base_rate_type="libor").
  - Row contains "ABR" => margin rate, base_rate="ABR" (base_rate_type="prime")
  - A separate single-row table referenced as "Facility Fee Rate" => fee rate, fee_basis="facility_commitment"
  - "L/C Fee Rate" tables => fee rate, fee_basis="letters_of_credit"

=== MULTI-REGIME PRICING (AMENDMENT PERIODS) ===
If the input shows multiple distinct pricing regimes (e.g., “prior to X”, “on or after Y”, “before the Revolving Facility Amendment Date”, etc.), you MUST:
1) Create a metric named "PricingRegime" with requires_non_compustat=true.
2) Create one tier_scheme PER regime (scheme_id ends with "_P1", "_P2", ...).
3) For EACH rate object for a multi-regime facility, include:
   "condition": { "metric": "PricingRegime", "op": "==", "value": 1 } (or 2,3...)
4) The source_refs for PricingRegime must cite anchors that contain the regime language.
5) PricingRegime is a synthetic routing metric (not an agreement-defined term), but definitions-v2 still needs it to be searchable:
   - Set PricingRegime.contract_term to a short verbatim phrase from the regime anchors (e.g., "prior to the Revolving Facility Amendment Date").
   - Set PricingRegime.search_tokens to 3–6 verbatim micro-phrases from the same anchors.
   - Do NOT leave BOTH contract_term="" and search_tokens=[].

If there is only one regime, do NOT include PricingRegime at all.
