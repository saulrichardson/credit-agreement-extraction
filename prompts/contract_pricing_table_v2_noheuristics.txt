You are extracting a SINGLE pricing table from a credit agreement into a strict JSON schema.

Input: TABLE_CONTEXT_JSON containing:
- One table (table_anchor_id, columns, rows, raw markdown)
- neighbor_anchors around the table (deterministic window)
- tail_anchors after the table until the next table (deterministic; may include footnotes/adjustments)
- Optional: table_plan (semantic hints from a separate planning step)
- Optional: global_adjustment_anchors (anchors elsewhere in the document that the scan identified as REQUIRED pricing adjustments)

Hard rules
- Output JSON only. No prose. No markdown.
- Valid JSON only.
- Do not invent facts.
- Your output must match EXACTLY the schema below (no extra keys).
- grid.table_anchor_id MUST equal the table_anchor_id provided in TABLE_CONTEXT_JSON.table.table_anchor_id.
- If the surrounding anchors (neighbor_anchors or tail_anchors) contain pricing adjustments (e.g., “reduced by 1.00%”, “increased by one basis point”), you MUST encode them as PricingAdjustment entries and cite the correct anchor_id(s) in source_refs.
- If global_adjustment_anchors is present:
  - These are additional adjustment anchors found elsewhere in the agreement by a full-document scan.
  - Only encode an adjustment from global_adjustment_anchors if it CLEARLY applies to this table/rate option.
  - When you do encode it, cite that anchor_id in adjustment.source_refs and adjustment.applies_when.source_refs.
- Percent-to-bps conversion:
  - 1.75% -> 175
  - 0.125% -> 12.5

Planner hints (authoritative when present)
- If TABLE_CONTEXT_JSON.table_plan is present:
  - Use table_plan.tiers_axis to decide which axis is tiers.
  - Use table_plan.rate_options_axis to decide which axis is rate options.
  - If table_plan.defined_term is present, it may define the fee/price label even if not present in the table itself.
  - If the plan seems inconsistent with the table, do NOT invent fields or add fake adjustments. Prefer the interpretation that is best supported by the table + anchors and keep the output strictly grounded.

Special case: "list-style" grids (common in older / non-table agreements)
- Sometimes the "table" is really prose or fixed-width text like:
  "<tier condition> <rate>"
  repeated for multiple tiers, and there is only ONE pricing output label (often a defined term like "Applicable Margin"
  or "Libor Option Rate").
- In that case:
  - Create EXACTLY ONE rate option for that output label (use table_plan.defined_term when present).
  - Create one tier per row/line (encode the thresholds as tier.tests when possible).
  - Create one cell per tier for that single rate option.
  - Do NOT create one "rate option" per row's numeric value (e.g., do not make "1.50%" a rate option label).
