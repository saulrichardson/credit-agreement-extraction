Modeling guidance (how to encode "pricing as code")
1) Facilities
   - Create Facility objects when the text clearly distinguishes facilities (revolving facility, term loan, swingline, LC).
   - If facilities are not clearly described in the provided anchors, leave facilities empty.

2) Rate options
   - Create RateOption objects for:
     - loan choices (e.g., "ABR Loans", "Base Rate Loans", "Term SOFR Loans", "Eurocurrency Loans")
     - fee rate labels (e.g., "Commitment Fee", "Letter of Credit Fee", "Fronting Fee", "Facility Fee")
   - `kind` is "loan" or "fee". Use `fee_basis` only if explicitly stated.
   - `label_raw` should be as close to verbatim as possible.

3) Variables (inputs)
   - Create PricingVariable objects for any metric used to select tiers or apply conditions, for example:
     - leverage_ratio (number)
     - consolidated_net_leverage_ratio (number)
     - ratings_level (rating or string)
     - is_default (boolean) if a Default-rate rule exists
   - Use `source_refs` to cite where the metric is defined or referenced.
   - Use `unit` hints when clear (e.g., "ratio", "rating_grade").

4) Tiering schemes
   - For each tiered pricing schedule, define a TieringScheme:
     - tiers: ordered labels (Tier 1 / Level I Status / etc.) with evidence
     - rules: TierRule objects that select the active tier using a Condition
     - default_tier_id: required (choose the most conservative/worst tier if unclear)
   - Condition encoding:
     - Always include `when.evidence` (near-verbatim text + source_refs).
     - `when.expr` MUST either be null OR follow the exact BoolExpr/NumExpr AST shape below.
       If you cannot produce a valid AST, set expr=null (do NOT invent your own "op/var_id/value" shape).

Expression AST cheatsheet (use exactly these keys)
- Numeric comparison:
  { "type": "num_compare", "op": "<=", "left": { "type": "var", "var_id": "leverage_ratio" }, "right": { "type": "const", "value": 3.0 } }
- AND / OR:
  { "type": "and", "args": [ <BoolExpr>, <BoolExpr> ] }
  { "type": "or", "args": [ <BoolExpr>, <BoolExpr> ] }
- NOT:
  { "type": "not", "arg": <BoolExpr> }
- Boolean variable (only when the agreement defines a boolean trigger):
  { "type": "var", "var_id": "is_default" }

5) Pricing parameters (the actual outputs)
   - Create PricingParameter objects for each distinct pricing output, such as:
     - applicable_margin_bps for loan options
     - commitment_fee_rate_bps for fee options
     - lc_fee_rate_bps / fronting_fee_rate_bps if specified
     - default_interest_spread_bps if specified
   - Each PricingParameter MUST have at least one PricingParameterRule.
   - Prefer TieredSchedule when tiers exist; FixedSchedule when the value is constant.
   - Schedule completeness:
     - For FixedSchedule: include exactly one RateValue per applicable rate_option_id.
     - For TieredSchedule: include a full tier x rate_option matrix of TierRateValue cells.
   - If the agreement provides adjustments (step-ups/step-downs, floors/caps), encode them as:
     - PricingAdjustment (delta_bps with conditions), and/or
     - PricingConstraint (min/max bps)
     with evidence and source_refs.
