Your task:
Given the full text of a CREDIT AGREEMENT (including schedules and pricing grids), produce ONE JSON object that captures all facilities and pricing terms in a consistent schema.

You must be CAREFUL, CONSERVATIVE, and FAITHFUL to the text:

- Prefer leaving fields null or empty over guessing.
- Do NOT invent facilities, fees, metrics, grids, rules, or rate formulas that are not clearly supported by the agreement.
- If you are unsure whether something is a distinct concept, OMIT it rather than hallucinate.

You may reason step‑by‑step internally, but your FINAL ANSWER must be ONLY the JSON object (no commentary).
```

## 1. Output format

Always output **exactly one** JSON object with this top-level shape:

```jsonc
{
  "effective_from": "",
  "base_currency": "",

  "indexes": [],
  "metrics": [],
  "facilities": [],
  "rate_options": [],
  "pricing_grids": [],
  "pricing_components": [],
  "rules": [],
  "overrides": []
}
```

* All top-level arrays must exist (they may be empty).
* If you cannot find a value in the document and there is no clear market-standard default, use `null` (or an empty string for text fields) and **do not guess**.

## 2. Object shapes

Use these shapes for the arrays.

### 2.1 Indexes (reference rates + their definitions)

```jsonc
"indexes": [
  {
    "index_id": "",
    "type": "",                // e.g. "SOFR", "TERM_SOFR", "DAILY_SOFR", "EURIBOR", "BASE_RATE", "PRIME", "FED_FUNDS", "FIXED", "OTHER"
    "currency": "",            // e.g. "USD", "EUR"
    "tenor": null,             // e.g. "1M", "3M", or null if not applicable

    "calculation_method": "",  // "external_published" | "composite" | "adjusted_index" | "other"
    "definition_text": "",     // short summary of the contract’s definition (may quote or paraphrase)

    "formula": null
    /*
    or, ONLY if the structure is clearly expressed in the agreement:

    "formula": {
      "aggregation": "sum" | "max" | "min",
      "components": [
        {
          "index_ref": null,   // another index_id, if the formula uses another defined rate
          "spread_bps": 0      // numeric spread added to that component in basis points
        }
      ],
      "floor_bps": null,       // numeric floor on the resulting rate, or null if none
      "cap_bps": null          // numeric cap on the resulting rate, or null if none
    }
    */
  }
]
```

**Guidance for rate definitions:**

* `definition_text`

  * Summarise the key mechanical part of the legal definition (how the rate is calculated in normal circumstances).
  * You may lightly quote or paraphrase; you do **not** need to reproduce every fallback and edge case.
  * If the definition is very complex, capture the main idea succinctly and ignore remote fallbacks.

* `calculation_method`

  * `"external_published"` – rate is simply taken from an external screen/publication (e.g. Term SOFR as published by CME, EURIBOR as published by EMMI, Prime Rate, Federal Funds Effective Rate).
  * `"adjusted_index"` – a published index plus/minus a fixed or defined adjustment and/or floor (e.g. Adjusted Term SOFR = Term SOFR + CSA, floored).
  * `"composite"` – the rate is defined as the **highest/lowest** of multiple underlying rates plus spreads (e.g. Alternate Base Rate = highest of Prime, Fed Funds + 0.50%, Term SOFR + 1.00%).
  * `"other"` – anything else that does not fit neatly above.

* `formula` (optional, conservative use)

  * Only fill `formula` when the calculation is clearly expressible as:

    * a max/min of several components (each = another index + spread), and/or
    * a simple sum of one index + a fixed spread, possibly with a floor/cap.
  * If you cannot confidently match the legal wording to this simple structure, set `formula: null` and rely on `definition_text` only.
  * Do NOT try to encode highly technical fallback waterfalls, compounding-in-arrears mechanics, or ARRC/ISDA-style conforming changes in `formula`. Those should remain in `definition_text` or be omitted if not essential.

* Underlying components:

  * If a composite index (like “Alternate Base Rate”) is defined using other rates (Prime, Fed Funds, Term SOFR, etc.), create separate `indexes` for those underlying rates if they are defined in the agreement, and refer to them via `index_ref` in the composite’s `formula`.
  * If the agreement mentions a component rate only inside the composite definition and does not define it separately, you may still create a simple `index` for clarity (with `calculation_method: "external_published"` and an appropriate `definition_text`), as long as you do **not** guess any missing details.

## 3. Global principles

1. **Faithfulness over completeness**

   * Only encode what is clearly in the agreement.
   * If a concept or number is not clearly stated or implied, **do not invent it**.

2. **No guessing**

   * If you are not sure a facility, fee, grid, rule, or rate formula exists, **omit it**.
   * If you cannot determine a numeric value, use `null` instead of guessing.

3. **Use metrics for anything that drives pricing**

   * Ratios, utilisation %, ratings, time triggers, ESG/KPI conditions, defaults, covenants, etc.
   * Your conditions in grids and rules must always be comparisons on metrics.

4. **Separation of concerns**

   * `indexes`: what the underlying reference rates are, including their **definitions and formulas**.
   * `rate_options`: which index a loan type uses + floor, frequency, day count, label.
   * `pricing_components`: all margins and fees.
   * `pricing_grids`: tables that map metrics → margins/fees/adjustments.
   * `rules`: overlays and conditional adjustments not naturally expressed as grids.

5. **Be conservative with rules and overrides**

   * Use `rules` only for genuine overlays (“+/- X bps relative to otherwise applicable”).
   * Use `overrides` only for explicit, short-dated manual patches (e.g. side letters with fixed date ranges).

6. **Basis points for recurring percentages**

   * All recurring percentage pricing (margins, unused fees, utilisation fees, etc.) must be in basis points:

     * 1.75% → `175`, 0.25% → `25`.

---

## 4. High-level process (internal)

Before writing JSON, internally:

1. Read the entire agreement once, including schedules.
2. Identify:

   * All facilities and sublimits.
   * All reference rates that are defined and used.
   * All concepts that affect pricing (metrics).
   * All pricing tables / grids / ratchets.
   * All margins and fees.
   * Any “if X then pricing changes” clauses.
3. Then fill the JSON in this order:

   1. Header (`effective_from`, `base_currency`)
   2. Facilities
   3. Indexes (with definitions)
   4. Metrics
   5. Rate options
   6. Pricing grids
   7. Pricing components
   8. Rules
   9. Overrides (if any)

Your final output must be **only** the completed JSON object.

---

## 5. Header

* `effective_from`: signing/effective date (`YYYY-MM-DD`) if clearly stated; otherwise `""`.
* `base_currency`: main deal currency (usually the primary revolver’s currency); if unclear, `""`.

---

## 6. Facilities

Create a `facility` for each commitment/loan with its own potential drawn/undrawn/LC balances or pricing.

* Use `type` to capture the high-level nature (revolving/term_loan/lc/swingline/bridge/capex/other).
* Use `limit` for revolving and LC facilities.
* Use `original_amount` for term loans.
* Use `parent_facility_id` when a sublimit is explicitly under another facility (e.g. LC sublimit under an RCF).

Do **not** create facilities for purely internal notions that never have their own pricing or balances.

---

## 7. Indexes & rate definitions (SOFR, Alternate Base Rate, etc.)

For every reference rate that actually defines an interest calculation or loan type, create an `index`:

1. Basic identity:

   * `type` – e.g. `"SOFR"`, `"TERM_SOFR"`, `"DAILY_SOFR"`, `"EURIBOR"`, `"BASE_RATE"`, `"PRIME"`, `"FED_FUNDS"`, `"FIXED"`, `"OTHER"`.
   * `currency` and `tenor` as applicable.

2. `definition_text`:

   * Read the defined term (e.g. “Term SOFR”, “Adjusted Term SOFR”, “Alternate Base Rate”) in the definitions section.
   * Capture the **main operational definition** in one or a few sentences:

     * For simple external benchmarks, state where the rate comes from (e.g. published screen).
     * For adjusted indexes (e.g. Adjusted Term SOFR), note that it’s the base rate plus an adjustment and any floor.
     * For composite rates (e.g. Alternate Base Rate/ABR), describe that it’s the highest/lowest of the listed components plus whatever spreads and floor.
   * You do **not** need to encode remote or highly technical fallback cascades (e.g. full benchmark replacement waterfalls). If they are very complex, you may omit those details from `definition_text`.

3. `calculation_method`:

   * `"external_published"` – rate is taken from a named screen/administrator (Term SOFR, EURIBOR, Prime Rate, Federal Funds Effective Rate, etc.).
   * `"adjusted_index"` – base index plus a defined fixed spread or adjustment and/or floor (e.g. Adjusted Term SOFR = Term SOFR + CSA, floored).
   * `"composite"` – rate is defined as highest/lowest of several base rates plus spreads (e.g. Alternate Base Rate highest of Prime, Fed Funds + 0.50%, Term SOFR + 1.00%, subject to a floor).
   * `"other"` – anything else.

4. `formula` (optional and only if clear):

   * Only use `formula` when you can clearly express the contract’s “normal case” as:

     * a sum of one rate + constant spread, or
     * a max/min of multiple rates each plus constant spreads.
   * Example – Adjusted Term SOFR:

     * `calculation_method: "adjusted_index"`
     * `formula` with `aggregation: "sum"` and one component = Term SOFR, plus spread in `spread_bps`, plus a `floor_bps` if clearly stated.
   * Example – Alternate Base Rate:

     * `calculation_method: "composite"`
     * `formula.aggregation: "max"`
     * components referencing `PRIME`, `FED_FUNDS`, `TERM_SOFR_1M` indexes plus their spreads, plus any overall floor in `floor_bps`.

If you’re not sure you can map the legal wording correctly into this structure, leave `formula` as `null` and rely only on `definition_text`.

## 8. Metrics

Create metrics only for concepts that **affect pricing**:

* Financial ratios (Total Net Leverage, Interest Coverage, etc.).
* Utilisation %, rating levels, ESG scores or KPI values.
* Time-based triggers (days since closing, months after closing).
* Boolean states (covenant breach, event of default, IPO completed, ESG targets met, etc.).

For each metric:

* `metric_id` – clear snake_case label (e.g. `"total_net_leverage"`, `"facility_utilisation_pct"`, `"state_event_of_default"`, `"esg_eligible"`).
* `type` – `"number"`, `"boolean"`, or `"rating_level"`.
* `source` – `"runtime_input"` if the value is provided by borrower or external sources; `"calculated"` if derived from other metrics, balances, dates.
* `description` – short phrase; ok to be simple or empty if obvious.

Do NOT create metrics for concepts that never influence margins or fees.

---

## 9. Rate options

A `rate_option` is a borrower’s choice of loan type (e.g. “SOFR loans”, “Base Rate loans”) for one or more facilities.

For each such choice:

* `facility_ids` – all facilities where this option is available.
* `index_ref` – the `index_id` that this option uses.
* `rate_floor_bps` – numeric floor on the reference rate (0 if none).
* `payment_frequency` – as per the agreement (monthly/quarterly/semi_annual/annual).
* `day_count` – day-count convention (`"ACT/360"`, `"ACT/365"`, etc.).
* `selection_value` – the label used in the agreement (“SOFR”, “Base Rate”, “EURIBOR”, etc.).

Never put margins or fees here; those belong in `pricing_components`.

---

## 10. Pricing grids

Use `pricing_grids` for tables or schedules that map **metrics** to **numeric values** (margins, fees, ESG adjustments, etc.).

* Each grid corresponds to one table (even if the table is split into “base” and “ESG” variants).
* `metric_refs` should list all `metric_id`s that appear in the grid’s row conditions.

Each row:

* `condition` – use combinations of `all_of`, `any_of`, `none_of`:

  * Normal band: use `all_of` only (e.g. leverage ≤ 2.5x).
  * Multi-metric band: include all relevant metric tests (e.g. leverage band AND utilisation band).
  * “Or” logic: either use `any_of` or separate rows.
* `values` – map each pricing number in that row (e.g. `margin_bps`, `commitment_fee_bps`, `utilisation_fee_bps`).

When the agreement describes **alternate grids** that apply only if an ESG or similar condition is met:

* Do NOT model this as grid switching logic.
* Instead, create a metric that captures the ESG condition (e.g. `esg_eligible`) and build **one combined grid** whose rows include that metric in the `condition`.

---

## 11. Pricing components

Every margin and every fee should be one `pricing_component`.

* Choose `category` (interest_margin, commitment_fee, utilisation_fee, lc_fee, upfront_fee, arrangement_fee, ticking_fee, amendment_fee, other).
* Define `scope` (which facilities and which rate options, if any).
* Choose `basis` (“drawn”, “undrawn”, “facility_limit”, “lc_outstandings”, “flat”).
* Choose `unit`:

  * `"bps_per_annum"` – recurring spreads/fees.
  * `"percent_flat"` – one-time % fees.
  * `"amount_flat"` – one-time fixed amounts.

Then either:

1. **Flat value (no grid)**

   * Use one of `base_value_bps`, `base_value_percentage`, `base_value_amount`.
   * Leave `grid: null`.

2. **Grid-driven**

   * Set all `base_value_*` to `null`.
   * Set `grid` with the grid id and `value_key` referencing the correct field in `values`.

Use basis points for all recurring percentages.

---

## 12. Rules

Use `rules` for conditional pricing changes that overlay the base grid / components:

* Step-ups or step-downs during covenant breaches, events of default, holidays, etc.
* ESG adjustments expressed as “± X bps relative to otherwise applicable margin”.
* MFN caps (“incremental facility margin cannot exceed existing by more than X bps”).
* Time-based overlays beyond simple grid expressions.

Each rule:

* `scope` – where it applies (facilities, specific components, or categories like `"interest_margin"`).
* `condition` – expressed via metrics using `all_of` / `any_of` / `none_of`.
* `effect`:

  * `"add_bps"` – add to current value; may be **negative** for discounts (ESG step-downs).
  * `"set_bps"` – override with a specific value.
  * `"cap_at_bps"` / `"floor_at_bps"` – impose absolute bounds.
  * `"cap_relative_to_metric"` – cap relative to another metric ± `offset_bps`.

Prefer a rule when the agreement clearly says “X bps more/less than otherwise applicable”.

---

## 13. Overrides

Use `overrides` only for explicit, short-dated manual adjustments with known date ranges (e.g. side letters that temporarily change pricing):

* One override per facility/category/date range.
* Set exactly one of `value_bps`, `value_percentage`, `value_amount`.
* Explain briefly in `reason`.

If the document expresses the change as a standard schedule or condition, use `pricing_grids` or `rules` instead.

---

Your final answer must be a single JSON object matching this schema. Do not include explanations, comments, or any text outside the JSON.
